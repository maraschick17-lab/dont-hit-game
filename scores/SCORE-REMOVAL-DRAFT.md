# Draft score removal operator handoff — not active
No new endpoint, no public deletion capability, no schema changes. This helper is deliberately not wired into server.js. It must not be deployed or used on production before Dot/owner confirms the procedure and authorized operator identity.

1. Accept a request via approved private support channel. Never ask for identity documents, account passwords, payment data, or database credentials. Public initials/score/time are searchable but not evidence that the requester owns the score. For a player request, require independently corroborated evidence (e.g. a private run reference or other reliable evidence); if none exists, escalate rather than claim ownership. For a moderation report, verify the actual content and apply documented criteria consistently. Do not publish private UUIDs.
2. Authorized operator uses existing securely managed DB access, ideally a least-privilege separate role with SELECT and narrowly scoped DELETE, no DDL. Preview via findCandidates; if ambiguous, do not choose arbitrarily. Case reference must not contain personal information. Record reviewer, reason, time and decision in private access-controlled case records, not repo or application logs.
3. Only following separate approved case decision, use one dedicated DB connection and removeReviewedScore with exact reviewed UUID and tuple. The confirmation object is a guardrail, not authentication: operator controls database session and must not expose this helper as an HTTP endpoint. Verify absence and unaffected neighboring rows read-only; treat ambiguous transaction outcome as unknown, not a success. Do not copy production DB data into CI.
4. Existing schema does not prevent a previously pending client retry from re-inserting the same UUID after deletion. Coordinate clearing pending submission if possible; check for reappearance and handle separately. A durable suppression registry would require separate storage approval; do not promise permanent deletion or an automatic retention deadline. Backups and hosting logs have separate retention. No production action authorized here.
5. CI uses temporary tables in a disposable PostgreSQL container. Approval and support publication remain separate.
